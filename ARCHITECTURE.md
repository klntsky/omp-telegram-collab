# Architecture

This document describes ownership and boundaries. User-visible requirements belong in [Product](PRODUCT.md). Setup and operational commands belong in [Development](DEVELOPMENT.md).

## Service composition

The CLI owns configuration management and starts the service. The running service composes Telegram bot adapters, persistent session storage, and the OMP runtime manager. A configured public HTTPS origin also enables the HTTP and WebSocket gateway. Bot adapters and the gateway share the runtime and session store, so Telegram and Mini App clients reach the same OMP conversation rather than maintaining independent agent state.

Configuration is the authority for project directories, bot identities, chat assignments, and service settings. Telegram owns group administrator roles. Neither roles nor runtime storage can override configured project assignments. The service coordinates reloads so components apply a validated configuration while managed host processes and histories remain independently recoverable.

The service configuration owns the Mini App mode. An empty public origin keeps the gateway stopped; a configured origin enables it. The bot adapter uses the same configuration to publish Mini App commands and launch controls. Network availability does not change this choice.

The service owns the readiness boundary: mandatory runtime and history checks, initialized bot identities and cached menus, a bound HTTP listener when the Mini App is enabled, and a successful first poll for every bot. Only after that boundary does it start adapter maintenance and the separately tracked online notification. Notification delivery is not a readiness dependency. Shutdown cancels the online task, drains input with update acknowledgements intact, and closes component-owned work before storage.

The bot adapter owns lifecycle-notice topic creation and delivery; the store preserves its per-bot, per-forum destination across restarts. The store owns durable topic detachment independently of session existence. Status-topic registration and `/detach` use the same transition, retaining history while rejecting session creation in that topic. The adapter uses that classification to exclude detached topics from prompts, session assignment, Git observation, and automatic title changes. Commands retain their normal authorization boundaries and may create separate topics, but cannot restore control of a detached destination.

Each adapter owns a cancellable background task set for session restoration, status maintenance, reconnects, and catalog refreshes. Readiness initialization does not start those lifecycles. Shutdown cancels waits and scheduled retries, fences late results from storage and Telegram side effects, and drains publication and delivery work. Runtime-owned discovery processes outlive an individual consumer only while another consumer still needs them.

The bot adapter enforces administrator authority using current Telegram supergroup membership. The shared predicate accepts human owners and administrators without requiring optional moderation rights. Telegram's native interface owns promotion and demotion; neither configuration nor SQLite supplies administrator grants. Local operators retain project-assignment authority. See [Product](PRODUCT.md#12-prompts-and-permissions) for command behavior.

The bot adapter owns the interactive settings panel and its message-bound choices, persisted by the store across restarts. Callback validation establishes the bot message, current panel revision, destination, and live administrator authority before an action runs. Configuration writes recheck the persisted assignment and authority at the write boundary. Successful saves persist their change history before menu refresh or Telegram rendering; rendering failures cannot discard that history, and displayed choices advance only after a confirmed edit. Forum defaults do not change the invoking topic's live session, and shared capacity controls identify their service-wide scope. Capacity changes use explicit adjustment buttons and confirmation; free-form settings replies belong to ordinary input handling, not the settings control boundary.

Admin listings share the current-member authorization boundary. The adapter reads Telegram's current administrator roster and excludes bots while retaining the owner. It rechecks membership and assignment before delivery. The displayed roster is informational; access-use checks fetch current membership independently.

The configuration layer owns the persistent service-termination switch. Telegram dispatch, gateway access and frame forwarding, and runtime admission recheck that switch at their respective boundaries, preventing a client or reconnect from bypassing suspension. Bot adapters invalidate pending interactions and invoke the runtime's identity-checked kill boundary; the service and Telegram polling stay alive.

## Telegram integration

Each bot adapter owns Telegram command handling, membership checks, prompt proposals, interactive questions, and transcript mirroring for its bot. It translates authorized user actions into runtime and Collab operations. It does not own OMP's conversation history or execute model turns itself.

grammY owns Telegram contexts and API transport. The bot adapter retains polling readiness, input ordering, cancellation, and shutdown acknowledgements rather than delegating those guarantees to framework-managed polling. The administration CLI uses grammY's API client without starting a poller.

The adapter owns process-local diagnostic observations for each session and project catalog. Prompt writes establish an unconfirmed observation; matching Collab receipts establish admission, not successful completion. Disconnect invalidates unconfirmed admission without inferring host exit. Runtime inspection remains read-only and reports failures as unknown state. Status reads those observations and the persisted catalog without invoking execution or recovery.

The status authorization boundary retains current-human membership, enrollment and assignment checks while allowing inspection during service suspension or degraded bot permissions. It rechecks membership and assignment before delivering diagnostic chunks and exposes only the current topic's session and assigned project's catalog. The normal action-authorization boundary remains unchanged and continues to enforce termination and bot permissions.

Interactive question answers cross the Collab UI-response boundary, not the prompt-submission boundary. Pending requests remain bound to their source destination and host lifecycle. Telegram delivery or a local button click is not evidence of host acceptance: completion receipts depend on the corresponding Collab confirmation, while force-termination completion depends on the runtime verifying process exit.

Topic destinations distinguish General from ordinary forum topics before business logic or storage access. The inbound Telegram boundary parses message and callback destinations; callers pass that identity rather than a database key. Storage alone encodes destinations into durable lookup keys. The outbound message adapter owns Telegram chat and thread routing for replies, sends, forwards, and service notices; its options exclude routing fields so callers cannot override the destination. Topic-management operations remain separate and require an actual session topic.

The inbound Telegram boundary normalizes raw text, media captions, and image references once and assigns each message or assembled album one intent. Command intent takes precedence over reply and ordinary-prompt intent; unknown or wrong-target slash commands remain ignored. Reply quotes supply prompt context, never command identity. Intent separates a new-topic task from an existing-session prompt, so ordinary all-message input in General creates a session topic rather than treating General as a session.

Receipt delivery and execution consume that same classified intent. The receipt consumer owns the received-message acknowledgement and its eligibility checks; it does not independently reinterpret the message or admit a task. Dispatch owns command execution, interactive answers, and authorized prompt admission. Receiving a Telegram message remains distinct from Collab accepting its prompt.

Receipt ingestion owns the durable destination for agent replies. Submission retains message provenance without advancing that destination; confirmed admission advances it before reaction delivery. The adapter snapshots the destination when queuing a reply so subsequent inputs cannot retarget its remaining chunks.

After prompt authorization, the adapter resolves Telegram image files and attaches their bytes to the Collab prompt. Prompt content can contain text, images, or both, without synthetic image instructions. Proposals, capacity waits, initial-task admission, persistence, and recovery retain the entire content; none may reduce an image-only task to missing text.

The inbound bot adapter distinguishes intentional replies from Telegram's implicit reply to a forum topic's creation message. Topic-root metadata establishes routing context, not user intent, even when the bot created the topic. The single classification boundary owns that distinction so metadata cannot bypass the configured prompt mode. The runtime receives only prompts admitted by that boundary.

The adapter groups image-album updates before prompt dispatch and keeps their place in the input queue, so a subsequent skill selection cannot alter an earlier album. The resulting prompt uses the same authorization, proposal, and image-admission boundaries as single-message input.

The bot adapter owns the user/topic-bound skill picker and its temporary inline-search context. It composes selected `/skill:name` references into authorized prompt text without implementing native skill-template expansion. Prompt admission and proposal creation own consumption of the pending selection; proposals retain the composed text independently of later picker changes.

The bot adapter owns the forum-default controls available to current Telegram owners and administrators. The configuration boundary validates canonical mentionable names without normalization; the adapter additionally checks catalog existence and current administrator membership before saving.

The delivery queue owns scheduling of queued Telegram output and its rate-limit delays, including relevance checks before retry. Ordinary output, topic names, and topic icons have independent execution capacity but share each chat's rate-limit boundary. Queue admission rechecks current eligibility and coalesces pending metadata by topic. Metadata request deadlines bound local waiting without claiming to cancel remote effects; late rate-limit responses still update the shared boundary. The Telegram API boundary owns explicit rate-limit recovery for calls outside that queue. It retries only rejected API requests, never whole user operations or ambiguous transport failures. Request cancellation and bot shutdown bound pending retry waits. The bot adapter sends agent output through Telegram's rich-message Markdown interface; Telegram owns parsing and presentation of native rich content. The adapter owns long-reply partitioning and topic and reply-target routing. Keeping delivery separate from session execution prevents Telegram scheduling from becoming the authority for whether OMP accepted a task.

The bot adapter owns topic metadata intent and process-local evidence of acknowledged writes. A private field state machine separates pending work, immutable dispatched attempts, disabled projection, and expiring confirmation. Stored display metadata is not proof of Telegram's current state. Native edit notices are observations unless their external attribution establishes new intent; ambiguous attribution cannot overwrite durable preferences. Conflicting observations invalidate the affected attempt rather than a newer goal, so delayed acknowledgments cannot erase known contrary evidence.

Collab snapshots and lifecycle events establish activity; the runtime's identity-checked discovery boundary establishes host absence. The adapter refreshes stale activity through a short-lived authenticated observation connection without replacing the primary listener or submitting work. Listener cancellation and activity revisions reject obsolete successes and failures. Missing or expired observations remain unknown and disable icon assertions. Existing-host mirror recovery is separate from read-only metadata observation, and authorized pending initial work retains its own admission workflow. Reconciliation revisits both uncertain and acknowledged projections because local cancellation cannot fence an edit already accepted by Telegram.

The stored topic lifecycle gates bot execution, mirroring, and gateway host admission. Closure advances the session generation and invalidates live connections and queued admission before cleanup. The adapter owns cancellation of unsent tasks and session interactions; the runtime owns targeted recovery and graceful retirement of managed hosts from durable identity. Closed-session reconciliation tracks unfinished retirement and restores the finish icon only after confirmed shutdown. Icon delivery does not reopen the topic, acquire Collab capabilities, or launch hosts. Terminal-owned attached hosts remain outside managed retirement.

The bot adapter owns two-way session-title reconciliation between Telegram topic updates and OMP's published session state. It separates the readable session title from the generated topic prefix. The runtime owns Git metadata discovery for the session's working directory; the adapter projects and restores that prefix without renaming the underlying OMP session. The store preserves pending readable Telegram renames and commits display names with their matching prefixes atomically. The adapter serializes native host-title mutations per session and reads current pending intent at dispatch without blocking frame ingestion. Telegram delivery does not acknowledge a pending host rename; the runtime boundary performs that mutation without submitting agent prompts.

## OMP execution and lifecycle

The runtime manager owns host discovery, startup, attachment, capacity, activity tracking, and process identity checks. Managed hosts run interactive OMP in PTYs under detached supervisors. The supervisor boundary lets hosts outlive a service process and lets the next service recover them. Attached hosts remain owned by their original terminal.

Host lifetime is separate from guest connection acquisition. Failed acquisition leaves an existing managed host running; startup rollback may retire only the host created by that acquisition attempt.

OMP owns worktree creation, change transfer, and live session relocation. The runtime requests OMP's native worktree operation and persists the resulting managed working-directory identity. A worktree-backed session retains its configured instance as the authorization and forum-assignment identity while its worktree supplies execution, history, model settings, and skill-discovery context. Recovery and force termination verify that execution identity rather than treating every session assigned to a repository as the same host. Worktrees remain independent durable filesystem state; host retirement and session shutdown do not remove them.

The runtime boundary owns skill-catalog discovery from OMP for the project and, when applicable, its session host. Bot adapters consume catalog names and descriptions through that boundary rather than inspecting OMP resources themselves.

The runtime owns per-working-directory catalog caching, shared in-flight discovery, and failure cooldowns. Managed sessions remain authoritative for their live loaded catalog; older managed hosts without skill-lifecycle support reject discovery with a restart instruction rather than approximate their catalog. Attached-host discovery uses assigned instance settings and cannot inspect terminal-private loaded skills. Discovery neither reloads OMP nor automatically restarts active hosts. Bot adapters own canonical-name eligibility, Telegram-safe skill aliases, and group-scoped command-menu publication. The service scheduler requests menu refreshes; adapters publish only changed menus. Refresh failures preserve original diagnostics and existing menus without blocking bot startup; new groups retain built-in commands.

The store owns durable snapshots of the last successful project catalog. Discovery runs independently per instance and yields snapshots; only menu publication is serialized. Publication rechecks current assignments before installing aliases, and failed discovery leaves the prior snapshot intact. Configuration reconciliation cancels obsolete catalog work and removes unauthorized listeners before publishing current cached menus; fresh discovery and restoration cannot hold up the configuration acknowledgement. Single-flight initialization installs identity and cached menus once, independently of maintenance.

OMP owns agent execution, conversation history, interactive questions, and live Collab state. The service connects as a Collab guest. It does not reconstruct an independent conversation from Telegram messages. Shared contracts describe communication between the service components and clients; they do not move execution authority into the browser.

Model-preset operations use a private host-control socket rather than model prompts. OMP owns native preset diagnostics and role precedence; managed-host controls must apply changes only to the session, never persist them into shared OMP role settings. Unsupported older or attached hosts cannot substitute a configuration-writing control path.

The runtime nominates idle-retirement candidates from activity observations and leases. The host-control boundary makes the final idle decision before accepting retirement. Unsupported hosts remain running. The runtime authorizes each retirement with a one-use private grant. Host acceptance atomically consumes that grant while publishing the retiring descriptor; cancellation removes the grant before admission can reopen. A replacement runtime revokes unaccepted grants under exclusive ownership before restoring managed admission. Accepted retirement remains distinct from observed process exit. Explicit force termination has a different boundary: the runtime must verify the intended process identity before signaling it. A database lock excludes another service from managing the same runtime data concurrently.

The lifecycle extension instance that creates a host's control server owns its descriptor and socket cleanup. Subagent and unstarted extension instances have no authority to remove the main host's control metadata.

## Durable and temporary state

The configuration layer owns validated, atomic updates to the protected YAML file. The session store owns durable Telegram topic mappings, enrollment state, session generations, recorded session metadata, and pending skill selections scoped by bot, chat, topic, and user. Pending selections survive service restarts and outlive the adapter's ten-minute inline picker context. OMP owns history files. Runtime bindings connect a Telegram session to its verified OMP identity and history rather than selecting whichever host happens to occupy a process identifier.

Pending initial tasks retain the submitting member and the authorizing administrator as separate admission identities. The bot checks current membership and administrator authority before submission, including recovery and explicit startup retries. The authorization boundary distinguishes confirmed membership or role denial from operational lookup failures and lifecycle cancellation. Only confirmed denial cancels pending admission; operational failures propagate without discarding the unsent task. Persisted actor identities are provenance, not permission grants.

New managed-topic creation snapshots the forum skill default into durable session state, independent of the creator and surviving bot restarts. Telegram prompt admission applies the snapshot only to the first accepted Telegram prompt or proposal and deduplicates it against explicit pending selections. New-topic prompts, including ordinary General input, compose it into their initial task before proposal freezing; manual topics use the first authorized user's accepted Telegram task. Later configuration changes do not rewrite existing topic snapshots or attached histories. The Mini App submission boundary does not apply or consume this Telegram composition state.

Bot adapters own temporary proposals and pending Telegram interactions. The gateway owns temporary connection tickets. The browser owns its local draft and rendered transcript. None of those temporary states can replace durable authorization or process identity.

## Gateway and browser

The HTTP gateway serves the Mini App and authenticates Telegram launch data for an initial exchange into a bot- and session-bound backend credential. The credential establishes identity for subsequent reconnects without requiring fresh Telegram launch data; current membership still gates admission. The ticket boundary retains flow-scoped read authorization server-side with each single-use connection ticket. The WebSocket gateway consumes that ticket and mediates Collab frames; loading the page alone does not grant host access.

The gateway keeps upstream room credentials on the server. Current Telegram membership authorizes a new connection flow; upgrade, initialization, transcript reads, and output reuse its read authorization without additional Telegram lookups. The gateway periodically refreshes that authorization and closes connections whose access is revoked, rather than expiring established identity on a timer. Local termination, enrollment, assignment, detachment, and session-generation checks remain independent of that snapshot and enforce local invalidation across asynchronous boundaries. Reconnects require a new flow. Read authorization is not a write capability.

Operational failures of the bot adapter's `getChat`/`getChatMember` authorization lookup are wrapped as `AuthorizationUnavailableError`, retaining the original message and error as `cause`. Telegram 4xx responses other than 429 retain their original error and remain terminal; transport errors, 429, 5xx, and lookup deadlines are recoverable. Each lookup has a ten-second deadline shared by its three Telegram reads. The bot bridges caller cancellation and service shutdown into Telegram's abort signal and races the reads against cancellation so ignored signals cannot retain authorization work. Caller and shutdown cancellation preserve their original reason; timers and listeners are released when the lookup settles. The HTTP gateway cancels abandoned authentication requests and pending admission on gateway shutdown, releases their capacity, and never issues credentials or tickets after cancellation. Validation, confirmed Telegram denial, and local lifecycle or assignment failures remain outside the recoverable boundary. The gateway fails closed on lookup unavailability: HTTP admission returns 503, and periodic refresh or queued authorization closes the socket with 1013 and the original diagnostic. Existing browser reconnection obtains fresh authorization without replaying actions; confirmed and local denials retain their existing 4003 socket behavior.

The bot adapter evaluates Mini App control using freshly fetched Telegram membership, the shared human owner-or-administrator predicate, and the stored session destination. The gateway independently admits each queued mutation using that current result, session lifecycle checks, and the raw host read-only restriction before any execution side effect. Runtime mutation callbacks refresh membership before join-triggered cold admission, capacity retirement, and host launch; the mirroring adapter does likewise before creating a listener with title side effects. Warm host and listener reuse do not refresh read authorization. The explicit action allowlist defaults to denial. Browser read-only state projects the flow's admitted role for presentation only; it cannot authorize writes. Local session, assignment, and generation checks are repeated across asynchronous admission boundaries.

Closed-session HTTP authorization establishes identity and administrator eligibility without issuing a connection ticket. Explicit reopening crosses the bot adapter's serialized Telegram mutation boundary, which refreshes administrator authority and checks the session generation before changing Telegram and stored topic state. Only an open session can receive a live-connection ticket; later gateway and runtime admission checks remain independent of the browser confirmation.

The Mini App owns presentation and client reconnection. It requests fresh authorization through the gateway rather than holding upstream host capabilities. Its transcript and draft are presentation state, not evidence that an instruction executed. The gateway transport consumes retryable gateway diagnostics without forwarding them as host errors, preserving retryability even before the host welcome arrives. The transport must not turn a reconnect into prompt replay.

## Trust boundaries

Telegram's signature establishes the caller's numeric identity and launch context. Current Telegram membership and administrator status determine the permissions enforced by the bot and gateway. Those checks protect access through this service; they cannot revoke an independently distributed OMP Collab capability.

The operating-system account is the filesystem and credential boundary. Project directories, chat assignments, and Telegram roles organize access inside the application but do not sandbox OMP processes. Isolation between mutually untrusted users requires an account or container boundary outside the application.

Local terminal attachment crosses the service account's private Unix control socket. Telegram supplies only a chat/topic lookup command after an administrator check. The service resolves the current enrollment, assignment, and session state and enforces them again at host admission. The local CLI starts the OMP guest client with the privately returned connection capability. Public HTTP routes do not provide this local attachment operation.

The private connection owns a runtime lease for the foreground terminal client. Disconnecting releases the lease. Service replacement closes local terminal connections so a lease cannot remain attached to an obsolete runtime generation.

When the Mini App is enabled, the reverse proxy or tunnel provides public HTTPS and forwards upgraded connections to the local service. Bot tokens and runtime data stay in protected server-side storage. The browser receives session access through the gateway, not direct ownership of the host's credentials.
