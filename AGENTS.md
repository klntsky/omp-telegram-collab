# Engineering principles

- No error message muting. Preserve the exact original error message when propagating or reporting a failure; never replace it with a generic summary. Add context without removing or rewriting the original diagnostic. Propagate the original error object where possible so subprocess exit codes, signals, and other diagnostic fields remain available. User-facing failure reports must retain the original message, including multiline diagnostics.
- Handle explicitly retryable service rejections inside the bot, respecting the service's retry delay and cancellation rather than asking the user to repeat an operation. Retry only the rejected request, not the entire user operation. Do not replay ambiguous failures that may already have applied side effects. Preserve original diagnostics for failures that cannot be recovered safely.
- When researching a question for the user, complete straightforward verification in the same research pass before answering. Check readily available repository code, installed dependency APIs and types, and authoritative documentation rather than deferring those checks or reporting easily resolvable uncertainty as follow-up work. Distinguish verified findings from checks that genuinely require unavailable access or user input.
- Before treating a Telegram test case as real or using it to justify a bug report or implementation change, always research online whether Telegram's de-facto server implementation can produce or accept that scenario. Check the Bot API server and TDLib implementation where relevant; matching a schema or constructing a valid-looking data shape is not proof of reachability. Cite the implementation evidence, distinguish source verification from live observation, and label unproven scenarios rather than presenting them as verified Telegram behavior.
- Within a single authorization flow, reuse the established authorization state for reads; do not repeatedly refresh it for read-only steps or delivery. Refresh authorization before writes and enforce current permissions at the mutation boundary. Do not reuse read authorization as permission to write.
- Commit as soon as you complete a feature and push every commit. Only deploy and restart the bot from master in the primary, non-worktree checkout. After every pull request merge, update that checkout, build there, restart the bot safely, and verify readiness. Never deploy or restart from a linked worktree, and never copy worktree-built artifacts into the deployed checkout. Outside pull request merges, restart the bot only when code changes; do not restart it for documentation-only or agent-instruction-only changes.
- Always register new or renamed Telegram slash commands in the appropriate Telegram command menus; handlers and `/help` text alone are not sufficient. Keep menu entries synchronized with command availability and retain server-side authorization checks for admin-only commands.
- This project is unpublished. Keep a single current schema and configuration format; collapse migrations and remove legacy compatibility paths rather than retaining shims or automatic imports.
- Keep test fixtures isolated per case. Prefer in-memory SQLite unless the scenario verifies disk persistence or restart behavior, and run test files with concurrency five.
- Do not assert on UI text surfaces: reply wording, captions, labels, rendered Markdown, status prose, or CLI display text. Assert meaningful authorization, persisted state, protocol data, and side effects instead. Delete presentation-only and mock-echo tests; combine related transitions into one scenario when they can share a fixture without losing isolation. Do not replace removed wording assertions with counts or bare success assertions that prove nothing important.
- The full test suite must pass on the pull request revision before merging. Do not run tests on master; build and verify service readiness there after deployment. Always set explicit command timeouts. A timeout is a failure to investigate, never a passing result. Diagnose the first failure before rerunning; a live process or recurring background logs are not evidence of progress. After a test run, rerun only failed tests, using file and test-name filters; do not rerun tests that already passed. Do not repeat a passing suite because of an unrelated edit. Run newly added tests directly.
- The coding agent owns master in the primary, non-worktree checkout. Tasks started there may make permanent requested changes there, commit, and push them. Tasks started in a linked worktree must remain on that branch, be committed and pushed there, and be delivered through a pull request. Do not switch to the primary checkout or transfer changes there to bypass this requirement. Worktree tasks must not deploy or restart the bot. Disposable pull request checkouts are for review and verification, not permanent implementation. Keep review-and-merge work scoped to the pull request rather than adding unrelated tooling.
- Do not revert or otherwise modify master to manufacture or reconstruct a pull request diff without explicit user approval.
- Use plain prose for a single-point chat response. For multiple points, use straightforward numbered lists starting at 1, with 1.1, 1.2, and similar numbering when grouping is necessary. This rule applies only to the AI coding agent's own chat responses, not product UI, Telegram bot messages, documentation, or other generated content; use the formatting appropriate to each surface.
- Do not use skill-specific jargon or internal workflow labels in user-facing responses. Describe the actual work and decisions in plain language, even when a skill asks you to announce its modes or principles.
- Do not include commit hashes, abbreviated commit IDs, or commit numbers in user-facing responses unless explicitly requested. Report that changes were committed without displaying an identifier.
- When referring to a GitHub branch in user-facing responses, link its full GitHub branch URL rather than mentioning only its name.
- When the user says "remember" a preference or instruction, update AGENTS.md with the durable rule rather than only acknowledging it in chat.
- When the user asks why you did something, quote the literal relevant AGENTS.md lines and include their line numbers. If no AGENTS.md rule supports the decision, say so explicitly rather than attributing it to an instruction.
- Use pnpm for package installation, dependency management, packaging, and package-script execution. Consumer instructions must use pnpm rather than the npm CLI; the npm registry remains the package distribution registry.
- Do not add temporary scripts, verification artifacts, or scratch files to `.gitignore`. Keep them outside the checkout or delete them when finished.
- Keep README.md focused on a brief product introduction, useful features, and consumer setup. Consumer installation, configuration, credentials, deployment, upgrades, restarts, and other normal deployment lifecycle operations belong in README.md, not DEVELOPMENT.md. Link to the other documents for developer operations and detailed product requirements.
- Keep current observable behavior and user-facing requirements in PRODUCT.md. Use meaningful numbered sections and bullets. Remove superseded requirements when behavior changes.
- Keep ARCHITECTURE.md focused on component responsibilities, state and side-effect ownership, dependency direction, and process and trust boundaries. Explain which boundary enforces each guarantee. Keep algorithms, schema versions, field layouts, constants, file inventories, and implementation steps in code.
- Keep DEVELOPMENT.md focused on development operations: contributor setup, local development execution, development credentials, build and test commands, and debugging. Consumer setup and normal deployment lifecycle operations are not development operations and belong in README.md. Keep test scenarios and coverage descriptions in test source, not Markdown.
- Maintain collapsible `<details>` examples in the README.md consumer setup instructions for CLI commands and their output, and for Telegram messages the bot sends during setup. Use clearly labeled filler names, IDs, paths, tokens, and request codes, never real credentials. Update the examples in the same change whenever setup commands, prompts, output, or bot messages change. Verify examples against the current implementation or exercised behavior; label excerpts and omitted prompts.
- Keep agent instructions and workflow rules in AGENTS.md. Do not duplicate product requirements in ARCHITECTURE.md or DEVELOPMENT.md; link to PRODUCT.md for context. Update the appropriate document whenever its contract changes, and remove obsolete text and references.
