# Engineering principles

- No error message muting. Preserve the exact original error message when propagating or reporting a failure; never replace it with a generic summary. Add context without removing or rewriting the original diagnostic. Propagate the original error object where possible so subprocess exit codes, signals, and other diagnostic fields remain available. User-facing failure reports must retain the original message, including multiline diagnostics.
- When researching a question for the user, complete straightforward verification in the same research pass before answering. Check readily available repository code, installed dependency APIs and types, and authoritative documentation rather than deferring those checks or reporting easily resolvable uncertainty as follow-up work. Distinguish verified findings from checks that genuinely require unavailable access or user input.
- Commit as soon as you complete a feature and push every commit. After every pull request merge, update the deployed checkout, build, restart the bot safely, and verify readiness. Outside pull request merges, restart the bot only when code changes; do not restart it for documentation-only or agent-instruction-only changes.
- Always register new or renamed Telegram slash commands in the appropriate Telegram command menus; handlers and `/help` text alone are not sufficient. Keep menu entries synchronized with command availability and retain server-side authorization checks for admin-only commands.
- This project is unpublished. Keep a single current schema and configuration format; collapse migrations and remove legacy compatibility paths rather than retaining shims or automatic imports.
- Keep test fixtures isolated per case. Prefer in-memory SQLite unless the scenario verifies disk persistence or restart behavior, and run test files with concurrency five.
- Use plain prose for a single-point chat response. For multiple points, use straightforward numbered lists starting at 1, with 1.1, 1.2, and similar numbering when grouping is necessary. This rule applies only to the AI coding agent's own chat responses, not product UI, Telegram bot messages, documentation, or other generated content; use the formatting appropriate to each surface.
- Do not include commit hashes, abbreviated commit IDs, or commit numbers in user-facing responses unless explicitly requested. Report that changes were committed without displaying an identifier.
- When referring to a GitHub branch in user-facing responses, link its full GitHub branch URL rather than mentioning only its name.
- When the user says "remember" a preference or instruction, update AGENTS.md with the durable rule rather than only acknowledging it in chat.
- Do not add temporary scripts, verification artifacts, or scratch files to `.gitignore`. Keep them outside the checkout or delete them when finished.
- Keep README.md focused on a brief product introduction and useful features. Link to the other documents instead of including setup instructions or detailed requirements.
- Keep current observable behavior and user-facing requirements in PRODUCT.md. Use meaningful numbered sections and bullets. Remove superseded requirements when behavior changes.
- Keep ARCHITECTURE.md focused on component responsibilities, state and side-effect ownership, dependency direction, and process and trust boundaries. Explain which boundary enforces each guarantee. Keep algorithms, schema versions, field layouts, constants, file inventories, and implementation steps in code.
- Keep setup, configuration, local execution, credentials, build and test commands, debugging, and deployment operations in DEVELOPMENT.md. Keep test scenarios and coverage descriptions in test source, not Markdown.
- Keep agent instructions and workflow rules in AGENTS.md. Do not duplicate product requirements in ARCHITECTURE.md or DEVELOPMENT.md; link to PRODUCT.md for context. Update the appropriate document whenever its contract changes, and remove obsolete text and references.
